# 视觉评审协议

> 何时需要人工评审、如何组织、如何记录。方案 §11.4 要求这项工作有协议，因为机器检查能发现错误，但判断不了「这版更好看」。
>
> 本协议的目的是让「这个改动是设计还是回归」这个问题有**可追溯的答案**，而不是每次重新争论。

---

## 一、为什么需要人工评审

自动检查能回答的问题：

| 问题 | 工具 |
|---|---|
| 页数是否一致？ | `migration.py check-parity` |
| 视觉是否相同？ | `visual_diff.py`（SSIM） |
| 文本是否丢失？ | `fidelity.py` |
| 结构是否有效？ | `validate.py` |

自动检查**不能**回答的问题：

| 问题 | 为什么 |
|---|---|
| 这版留白是否更舒服？ | 审美判断 |
| 标题层级是否传达了正确的从属关系？ | 语义判断 |
| 这段强调是否过度？ | 语气判断 |
| 这个改动是优化还是退化？ | 需要知道意图 |

**结论**：机器判「对不对」，人判「好不好」。

---

## 二、何时触发评审

| 触发条件 | 必须评审 |
|---|---|
| 有意改变页面视觉 | ✅ |
| SSIM < 0.999 但与基线一致 | ✅ 确认是否有意 |
| 新增或修改模板 | ✅ |
| 修改投影规则 | ✅ |
| 字体清单变更 | ✅ |
| 纯文本内容变更（CSS 不动） | ❌ 不必 |
| 纯脚本重构（渲染不变） | ❌ 不必 |

**判定方法**：

```bash
python3 scripts/fidelity.py measure          # 7/7 且 SSIM 1.0000 → 无需评审
python3 scripts/visual_diff.py before.pdf after.pdf   # SSIM < 0.999 → 需要评审
```

## 三、评审流程

### 步骤 1：准备对照

**固定变量**：同内容、同字体、同页面参数、同分辨率。

```bash
# 生成 A/B 对照
python3 scripts/review_pair.py \
  --before dist/before.pdf \
  --after  dist/after.pdf \
  --out    dist/review/
```

产物：
- `review/A.png`、`review/B.png`（**随机标记**，不透露新旧）
- `review/answer.json`（映射关系，评审后才揭示）
- `review/side-by-side.png`（并排对照）

### 步骤 2：排除硬缺陷

**在审美评审之前**，先确认没有 correctness 缺陷：

```bash
python3 scripts/quality_vector.py dist/after.pdf --genre <genre>
```

若 `correctness` 为 FAIL（文本丢失、页数超合同、缺字），**停止审美评审** —— 先修缺陷。

理由：讨论「哪个更好看」时若其中一版丢失了内容，讨论没有意义。

### 步骤 3：独立判断

| 规则 | 说明 |
|---|---|
| **两名评审者** | 各自独立，不讨论 |
| **不知道新旧** | 只看到 A 与 B |
| **先选后说** | 先记录选择，再写理由 |
| **允许「无差异」** | 若确实看不出，如实记录 |

**记录格式**：

```json
{
  "reviewer": "reviewer-1",
  "choice": "B",
  "confidence": "clear | slight | guessing",
  "defects": [
    {"type": "heading-orphan", "severity": "P1", "where": "page 3"}
  ],
  "note": "B 的章节间距更均匀，但第 3 页标题孤立"
}
```

### 步骤 4：归纳

| 情形 | 处理 |
|---|---|
| 两人都选新版 | 接受 |
| 两人都选旧版 | **拒绝**，回滚 |
| 分歧 | 记录双方理由，保留案例，由主审复核 |
| 都选「无差异」 | 接受（改动无视觉影响） |

**禁止**：以简单多数票**删除事实**。分歧本身是信息。

## 四、缺陷分类（taxonomy）

### 11 类缺陷

| # | 类型 | 含义 | 典型来源 |
|---|---|---|---|
| 1 | `semantic-loss` | 内容丢失或错序 | IR/writer |
| 2 | `overflow` | 越界、裁切、重叠 | 布局 |
| 3 | `font` | 缺字、非预期回退 | 字体 |
| 4 | `line-break` | 断行不当、禁则违反 | 断行规则 |
| 5 | `spacing` | 间距不均、节奏断裂 | 间距 |
| 6 | `heading-orphan` | 标题孤立于页尾 | 分页 |
| 7 | `figure-caption` | 图注脱离图表 | 浮动 |
| 8 | `page-density` | 页面过空或过密 | 分页 |
| 9 | `alignment` | 对齐不一致 | 网格 |
| 10 | `contrast` | 对比度不足（可访问性） | 主题 |
| 11 | `taste` | 纯偏好，无客观错误 | 审美 |

### 严重性分级

| 级别 | 含义 | 处理 |
|---|---|---|
| **P0** | 发布阻断：内容丢失、无法阅读 | 必须修 |
| **P1** | 实质缺陷：明显错误，影响阅读 | 应修 |
| **P2** | 打磨项：不完美但不影响理解 | 可延后 |
| **P3** | 偏好：无客观标准 | 记录，不阻断 |

### 分级原则

| 判断 | 归属 |
|---|---|
| 客观错误（有唯一正确答案） | 规则检查，P0–P1 |
| 稳定专业共识（有公认标准） | rubric + 重复样例，P1–P2 |
| 依赖文档类型/语言 | 由 Genre/Language context 约束，P2 |
| 纯偏好 | **不做通用 hard gate**，P3 |

## 五、记录与追溯

### 每次评审必须留下

| 项 | 内容 |
|---|---|
| 触发原因 | 什么改动触发了评审 |
| 对照产物 | A/B 图 + side-by-side |
| 评审者 | 至少两人 |
| 判断 | 选择 + 信心 + 缺陷 |
| 结论 | 接受 / 拒绝 / 待定 |
| 若接受 | 基线更新理由 |

### 存放位置

```
docs/reviews/
  YYYY-MM-DD-<change>.md     评审记录
dist/review/                 对照产物（不入库）
```

**基线更新必须先有评审记录**，这是 `document_baseline.py capture --approval-reason` 要求非空理由的原因。

## 六、与自动检查的关系

```
自动检查（每 PR）
  ↓ 发现 SSIM 变化
人工评审（按需）
  ↓ 判断变化性质
基线更新（需理由）
  ↓
记录归档
```

| 层 | 回答 | 频率 |
|---|---|---|
| 自动 | 变了没有 | 每次 |
| 人工 | 变好还是变坏 | 按需 |
| 基线 | 接受这个变化吗 | 有理由才更新 |

---

## 七、本协议不做什么

| 不做 | 理由 |
|---|---|
| 不做通用美观评分 | 无客观标准，会变成数字游戏 |
| 不用多数票删除事实 | 分歧是信息，不是噪声 |
| 不让 CI 自动批准 | 批准需要人 |
| 不强制每个改动都评审 | 纯内容改动无视觉影响 |

## 八、工具

| 工具 | 作用 |
|---|---|
| `scripts/review_pair.py` | 生成 A/B 对照 |
| `scripts/visual_diff.py` | 量化差异（SSIM） |
| `scripts/quality_vector.py` | 排除硬缺陷 |
| `scripts/document_baseline.py` | 更新基线（需理由） |

**协议的可执行部分由 `review_pair.py` 实现**，本文件说明何时用、如何判断、如何记录。
