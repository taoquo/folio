# 引擎实施规范

> 本文规定**如何改动这个引擎**，以及**如何证明改动确实生效**。
>
> 它存在的理由是一次真实的失误：IR 引擎建成、测试覆盖、文档齐全、连续多轮验证通过，却**不在产出交付物的路径上**。所有既有检查都在问「这个模块对不对」，没有一个问「主力产出走没走它」。

---

## 一、那次失误的完整复盘

### 发生了什么

| 事实 | 发现时间 |
|---|---|
| IR 引擎建成（13 个模块、验证器、writer） | 第 1 轮 |
| 885 测试通过 | 每轮 |
| `fidelity` 7/7 SSIM 1.0000 | 每轮 |
| 八项门禁全绿 | 每轮 |
| **`assets/examples/` 由 `build.py` 生成，不经过 IR** | **最后一轮** |

### 为什么没被发现

四类验证各自回答一个问题，**没有一个回答「谁在用」**：

| 验证 | 回答的问题 | 为何漏掉 |
|---|---|---|
| `unittest` | 模块行为对不对 | 单元正确即通过 |
| `fidelity` | 两条路径像不像 | 两者各自正确即通过 |
| `census`（旧版） | 能力**存在**吗 | 文件在、能运行即通过 |
| 门禁 | 产物有效吗 | 可解析即通过 |

### 根因

> **「存在」被当成了「生效」。**

`census` 检查的是 `Path(f).is_file()` 与「命令能跑通」。一个只被测试引用的模块，**完全满足**这两个条件。

## 二、规范条文

### 规则 1：能力必须可达

**任何新增能力，必须说明它被哪条生产路径调用。**

| 要求 | 检查方式 |
|---|---|
| 声明调用它的路径 | 在 PR 说明中写明 |
| 该路径确实调用它 | `architecture.py check` |
| 不是「仅测试引用」 | 同上 |

**生产路径的定义**（会产出交付物的）：

- `scripts/build.py` — 模板渲染、示例、图表
- `scripts/document_build.py` — 内容构建

**不构成可达性的**：

| 情形 | 为何不算 |
|---|---|
| 只被 `tests/` 引用 | 测试不产出交付物 |
| 只被诊断工具引用 | `spacing_probe`、`box_inspector` 是观察者 |
| 只有 CLI 入口 | 无人运行的 CLI 等于不存在 |
| 只被 `__init__` 导出 | 导出不等于调用 |

### 规则 2：分层不可逆

| 层 | 可以引 | 不可引 |
|---|---|---|
| **语义核心**（`model`、`validate`、`bridge`、`containers`） | 标准库、IR 自身 | 任何渲染库 |
| **writer**（`writers/`） | 格式库（`pptx` 等） | — |
| **渲染边界**（`renderers/`） | 渲染库 | `document_ir` 的语义实现 |
| **上层的构建路径** | 全部 | — |

**理由**：语义核心描述「意思」，命名渲染库就把意思绑到了一个后端。

### 规则 3：文档中的默认值必须与代码一致

`AGENTS.md` 或 `integration-status.md` 声明某开关默认 `on`，代码必须默认 `on`。

**检查**：`architecture.py check` 的 `declarations` 部分。

### 规则 4：验证必须覆盖「生效」，不只是「正确」

新增能力的验证**至少包含一项**：

| 验证类型 | 例子 |
|---|---|
| 端到端可达 | 「构建 X 后，产物包含 Y」 |
| 调用链存在 | `architecture.py check` |
| 行为差异 | 「开启时与关闭时结果不同」 |

**反例**（不充分）：

- 「函数返回正确值」—— 不证明它被调用
- 「文件存在」—— 不证明它被使用
- 「测试通过」—— 不证明它影响产物

### 规则 5：开关必须有开它的路径

新增一个默认关闭的能力，**必须同时说明谁会在什么条件下开启它**。

| 情形 | 判定 |
|---|---|
| 有代码路径可开启 | 合规 |
| 只能手工设环境变量 | **需在文档中写明场景** |
| 无任何开启路径 | **不合规** —— 那是死代码 |

**当前违规**：`gap_projection` 默认关闭且无开启路径（见第六节）。

## 四、改动流程

### 新增一个能力

```
1. 在文档中声明它被哪条生产路径调用
2. 实现
3. 让那条路径调用它
4. 运行 architecture.py check   ← 必须无 error
5. 运行 census.py              ← 通过率不下降
6. 运行 fidelity.py measure     ← 7/7 SSIM 1.0000
7. 运行 unittest discover       ← 全绿
```

**第 3 步不可跳过**。第 1 步的声明若在第 4 步不成立，检查会失败。

### 修改一条生产路径

| 步骤 | 要求 |
|---|---|
| 1 | 说明改动影响哪条路径 |
| 2 | 运行 `architecture.py check` |
| 3 | 验证产物未退化（`fidelity`、页数） |
| 4 | 若改变默认值，同步文档 |

## 六、修复顺序

按「先低风险、后高风险」排列：

| 顺序 | 修复 | 风险 | 理由 |
|---|---|---|---|
| 1 | `document_build` 走 `pipeline` | 低 | 接口已存在 |
| 2 | `document_build` 走 `renderers` | 低 | 协议已存在 |
| 3 | 接入 `migrations` | 低 | 只在读取时加检查 |
| 4 | 接入 `containers` | 低 | 已实现，只在 bridge 中调用 |
| 5 | `gap_projection` 给出开启路径 | 低 | 已验证 SSIM 1.0 |
| 6 | `build.py` 委托 `document_build` | **中** | 职责混杂，需分批 |

**前 5 项风险都低**，可一次完成。第 6 项是真正的架构改动，需单独规划。

---

## 七、为什么这些规则有效

| 规则 | 防止的失误 |
|---|---|
| 可达性检查 | 「建成了但没接上」 |
| 分层检查 | 「语义层绑定后端」 |
| 默认值一致性 | 「文档说开、代码是关」 |
| 验证覆盖生效 | 「测试通过但没影响产物」 |
| 开关开启路径 | 「死代码」 |

**核心原则**：

> **一个能力只有到达产物，才算存在。**

存在性由**调用链**证明，不由**文件存在**证明。
